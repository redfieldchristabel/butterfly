## Choose a base class

| Situation | Base class |
| --- | --- |
| Your sign-in API returns the complete app user | `AuthServiceRepository<T>` |
| A provider supplies identity and your app loads additional profile data | `IdentityAuthRepository<I, T>` |
| Firebase Auth supplies identity | `FirebaseAuthManagementRepository<T extends FirebaseUser>` |
| OAuth2 supplies an authenticated HTTP session | `BaseOauth2AuthManagement<T>` |

The base `auth_management` package does not implement email/password sign-in, registration, password reset, or a concrete static `AuthService`. Those belong in your application or provider integration.

Authentication is state-management-agnostic. BLoC/Cubit, Provider, a `StreamBuilder`, or another state manager can consume `streamUser()` and call the service methods directly. Riverpod is the supplied adapter, not a requirement. To keep another library in sync automatically, implement `AuthServiceProviderRepository<T>` from `auth_management_provider.dart` and return it from `providerRepo`; see [Riverpod integration](/libraries/auth/features/riverpod#other-state-managers).

## Service for an API that returns the user

This example injects a login function and a cache. The login function is application code, not a Butterfly API.

<Info>Only `lib/main.dart` is a fixed name. Files marked **(suggested)** follow the `butterfly init` layout; rename or move them freely. Replace `my_app` in imports with the `name` from your `pubspec.yaml`.</Info>

```dart title="lib/models/app_user.dart (suggested)"
class AppUser {
  const AppUser(this.id);
  final String id;
}
```

```dart title="lib/services/auth.dart (suggested)"
import 'package:auth_management/auth_management.dart';
import 'package:my_app/models/app_user.dart';

class AuthService extends AuthServiceRepository<AppUser> {
  AuthService({required this.dbRepo, required this.login});

  @override
  final AuthManagementDatabaseRepository<AppUser> dbRepo;
  final Future<AppUser> Function(String email, String password) login;

  Future<void> signIn(String email, String password) async {
    final user = await login(email, password);
    await dbRepo.addUser(user);
  }
}
```

Initialize the chosen cache first, then call `authService.initialize()` once before relying on `currentUser`. It registers the service in static `AuthServiceRepository.instance` and subscribes to `streamUser()`. The singleton is `late final`, so initializing another service in the same isolate is not supported.

`currentUser` is an **instance field**, initially null and updated when the subscription receives an event. Initialization is not a synchronous guarantee that a persisted user has already been emitted. Model startup/loading separately when a route guard must distinguish unresolved state from signed out.

## Public service contract

| Member | Behavior |
| --- | --- |
| `dbRepo` | Required local-user repository |
| `providerRepo` | Optional state-management bridge, published to on every user change and cleared on sign-out; defaults null |
| `getUser()` | Reads the current user; base class delegates to the cache |
| `streamUser()` | Emits user changes; base class delegates to the cache |
| `currentUser` | Most recent user received by the initialized service |
| `signOut()` | Clears cache, then optional provider state |
| `onUserChanged(T? user)` | Hook after `currentUser` updates |
| `onUserError(Object error, StackTrace stackTrace)` | Stream-error hook; default logs the error |

There is no `userStream` getter. Use `streamUser()`. Base sign-out does not revoke a custom backend session; override it if your backend requires that. After `initialize()`, every user change is forwarded to `providerRepo` automatically; see [Riverpod integration](/libraries/auth/features/riverpod).

## Identity resolution

`IdentityAuthRepository<I, T>` adds `streamIdentity()`, `getIdentity()`, `fetchUser(identity)`, `isCachedUserFor(cachedUser, identity)`, and `refreshUser()`.

Resolution follows this order:

1. No identity: clear the local cache and resolve null.
2. A cached user matches the identity: reuse it without calling `fetchUser`.
3. Otherwise: fetch the app user, save it to `dbRepo`, and resolve it.

The identity stream must emit its initial identity and later changes. The repository shares a pending fetch between concurrent resolutions and replays its latest emitted user to later `streamUser()` listeners. `getUser()` resolves independently and returns its result; it does not itself call the stream's emission method.

Implement `fetchUser` to return the full app model. Do not write to `dbRepo` inside it or call `getUser`, `streamUser`, or `refreshUser` recursively. `isCachedUserFor` defaults to true, so custom providers must override it when switching accounts could otherwise reuse another user's cached data. Firebase supplies a UID comparison.

## Refresh, errors, and lifecycle limits

`refreshUser()` bypasses the cache, fetches again, checks the current identity, saves and emits the result. It returns null if signed out or if the fetched user no longer matches the current identity. It does not clear a cache when called while signed out. Provider profile changes are not automatically database subscriptions.

An identity-resolution error is emitted on the user stream; a failing `getUser()` or `refreshUser()` throws to its caller. `currentUser` retains its previous value on a stream error. Handle that explicitly rather than assuming it becomes null.

The ordinary resolution path does not recheck the current identity after every awaited fetch; do not assume full account-switch race protection. The service and identity repository do not expose a public disposal method for their internal subscriptions. Design one application-owned service, not a new service per screen.
