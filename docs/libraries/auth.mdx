`auth_management` separates authentication into four distinct concerns so your UI and domain logic never depend on a specific database or identity SDK:

<CardGroup cols={2}>
  <Card title="1. Service & Identity" icon="key">
    `AuthServiceRepository<T>` or `IdentityAuthRepository<I, T>` coordinates sign-in, session restoration, and `currentUser`.
  </Card>
  <Card title="2. Local User Cache (dbRepo)" icon="database" href="/libraries/auth/features/datasources">
    `AuthManagementDatabaseRepository<T>` persists your `AppUser` locally (Sembast, Hive CE, Isar, or memory).
  </Card>
  <Card title="3. Identity Providers" icon="id-card" href="/libraries/auth/features/providers">
    Firebase Auth, Google Sign-In, or OAuth2 adapters emit raw identity changes and resolve your `AppUser` via `fetchUser`.
  </Card>
  <Card title="4. State Bridge (providerRepo)" icon="bolt" href="/libraries/auth/features/riverpod">
    `AuthServiceProviderRepository<T>` automatically syncs every user change and sign-out event into Riverpod (`userProvider`) or any other state manager.
  </Card>
</CardGroup>

## Which base class should I extend?

| Scenario | Base Class to Extend | Package |
| --- | --- | --- |
| Your own backend login endpoint returns `AppUser` directly | `AuthServiceRepository<T>` | `auth_management` |
| An external SDK emits an identity `I` and you fetch `AppUser` separately | `IdentityAuthRepository<I, T>` | `auth_management` |
| Firebase Auth supplies `firebase.User` identity | `FirebaseAuthManagementRepository<T extends FirebaseUser>` | `auth_management_firebase` |
| An OAuth2 server supplies an `oauth2.Client` session | `BaseOauth2AuthManagement<T>` | `auth_management_oauth2` |

## Custom API auth service: Butterfly vs. Raw Dart

<Info>Only `lib/main.dart` is a fixed name. Files marked **(suggested)** follow the `butterfly init` layout; rename or move them freely. Replace `my_app` in imports with the `name` from your `pubspec.yaml`.</Info>

<Tabs>
  <TabItem label="With Butterfly" value="with-butterfly">
    Extend `AuthServiceRepository<AppUser>`, provide `dbRepo`, and write your `signIn` method—`currentUser` tracking, `streamUser()`, `signOut()`, and `providerRepo` synchronization come built in:

    ```dart title="lib/models/app_user.dart (suggested)"
    class AppUser {
      const AppUser(this.id);
      final String id;
    }
    ```

    ```dart title="lib/services/auth.dart (suggested)"
    import 'package:auth_management/auth_management.dart';
    import 'package:my_app/models/app_user.dart';

    class AuthService extends AuthServiceRepository<AppUser> {
      AuthService({required this.dbRepo, required this.login});

      @override
      final AuthManagementDatabaseRepository<AppUser> dbRepo;
      final Future<AppUser> Function(String email, String password) login;

      Future<void> signIn(String email, String password) async {
        final user = await login(email, password);
        await dbRepo.addUser(user);
      }
    }
    ```
  </TabItem>
  <TabItem label="Without Butterfly (Raw Dart)" value="without-butterfly">
    Without `auth_management`, you maintain a broadcast `StreamController<AppUser?>`, track `currentUser` manually, wire subscription error handling, and coordinate cache writes and clears on `signIn` / `signOut`:

    ```dart title="lib/models/app_user.dart (suggested)"
    class AppUser {
      const AppUser(this.id);
      final String id;
    }
    ```

    ```dart title="lib/services/auth.dart (suggested)"
    import 'dart:async';
    import 'package:my_app/models/app_user.dart';

    class AuthService {
      AuthService({required this.login});

      final Future<AppUser> Function(String email, String password) login;
      final StreamController<AppUser?> _controller =
          StreamController<AppUser?>.broadcast();

      AppUser? currentUser;

      Stream<AppUser?> streamUser() => _controller.stream;

      Future<void> signIn(String email, String password) async {
        final user = await login(email, password);
        currentUser = user;
        _controller.add(user);
      }

      Future<void> signOut() async {
        currentUser = null;
        _controller.add(null);
      }

      void dispose() {
        _controller.close();
      }
    }
    ```
  </TabItem>
</Tabs>

### Startup & initialization rules

1. **Initialize storage first:** Open/initialize your `dbRepo` adapter before calling `authService.initialize()`.
2. **Call `authService.initialize()` once:** Sets the singleton `AuthServiceRepository.instance` (`late final`) and subscribes to `streamUser()`. Because `instance` is `late final`, initializing a second `AuthServiceRepository` in the same isolate throws a `LateInitializationError`.
3. **Understand `currentUser` timing:** `currentUser` starts as `null` and updates asynchronously as `streamUser()` emits. If your splash screen or route guard needs to distinguish *"still restoring cached session"* from *"signed out"*, track an explicit initialization flag alongside `currentUser`.

## `AuthServiceRepository<T>` contract

<Property name="dbRepo" type="AuthManagementDatabaseRepository<T>" required>
  The local cache storing your `AppUser`. Base `getUser()` and `streamUser()` delegate to `dbRepo` unless overridden by `IdentityAuthRepository`.
</Property>

---

<Property name="providerRepo" type="AuthServiceProviderRepository<T>?" optional>
  Optional state-management bridge (defaults to `null`). Once `initialize()` runs, every `streamUser()` emission automatically calls `providerRepo?.sync(user)` before invoking `onUserChanged`, and `signOut()` calls `providerRepo?.sync(null)`.
</Property>

---

<Property name="currentUser" type="T?">
  Instance field holding the latest user emitted after `initialize()`. Remains unchanged if `streamUser()` emits an error.
</Property>

---

<Property name="getUser() / streamUser()" type="FutureOr<T?> / Stream<T?>">
  Reads or watches the authenticated user. Note that the method is `streamUser()`, not a `userStream` getter.
</Property>

---

<Property name="signOut()" type="Future<void>">
  Calls `dbRepo.clearUser()` and `providerRepo?.sync(null)`. Override `signOut()` if your backend also requires a token-revocation HTTP call.
</Property>

---

<Property name="onUserChanged(T? user) / onUserError(Object error, StackTrace stackTrace)" type="void">
  Lifecycle hooks triggered by the `initialize()` stream subscription. Override `onUserChanged` to notify a `GoRouter` `refreshListenable`, or `onUserError` to report stream failures (default logs via `dart:developer`).
</Property>

## How `IdentityAuthRepository<I, T>` resolves profiles

When using Firebase, OAuth2, or your own external identity provider, `IdentityAuthRepository<I, T>` bridges raw identity `I` to your domain model `T`:

<Steps>
  <Step title="Identity stream emits" icon="satellite-dish">
    `streamIdentity()` emits the initial identity `I?` and any subsequent auth state changes.
  </Step>
  <Step title="Null identity → clear cache" icon="eraser">
    If `identity == null`, the repository calls `dbRepo.clearUser()` and emits `null`.
  </Step>
  <Step title="Cache hit → reuse without network fetch" icon="bolt">
    If `dbRepo.getUser()` returns a cached `T` **and** `isCachedUserFor(cachedUser, identity)` returns `true`, the cached user is returned immediately without calling `fetchUser`.
  </Step>
  <Step title="Cache miss → fetchUser(identity) & persist" icon="cloud-arrow-down">
    Calls your `fetchUser(identity)` implementation, writes the returned `T` to `dbRepo.addUser(user)`, and emits it. Concurrent callers share the in-flight fetch future, and late subscribers to `streamUser()` immediately receive the last resolved user.
  </Step>
</Steps>

<AccordionGroup>
  <Accordion defaultOpen title="Rules for implementing fetchUser and isCachedUserFor">
    - **Keep `fetchUser` pure:** Only fetch and return `T`. Never call `dbRepo.addUser`, `getUser()`, `streamUser()`, or `refreshUser()` inside `fetchUser` (doing so causes redundant writes or infinite recursion).
    - **Always override `isCachedUserFor` on custom providers:** The base default returns `true` for every non-null user! If a user signs out and signs into a different account before the cache clears, a `true` default would reuse the previous account's cached profile. (`FirebaseAuthManagementRepository` already overrides this to compare `cachedUser.firebaseUid == identity.uid`.)
  </Accordion>
  <Accordion title="Force-reloading profile data with refreshUser()">
    Cached profiles are reused across restarts and token refreshes. When the user edits their profile on the server, call `await authService.refreshUser()` to bypass `dbRepo`, run `fetchUser(identity)` fresh, verify the identity hasn't changed, update `dbRepo`, and broadcast the new `T` on `streamUser()`.
  </Accordion>
</AccordionGroup>
