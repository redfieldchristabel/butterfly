## Choose the service

Extend `GoRouterService` for routing without authentication guards. Extend `GoRouterAuthRoute<T>` for user-aware guards and implement both `routes` and the synchronous `user` getter. The auth-aware class is an abstract class, not a mixin, and requires its separate import.

```dart
import 'package:core_management_route_go_router/go_router_auth_route.dart';
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

class AppUser {
  const AppUser(this.id);
  final String id;
}

class AppRoutes extends GoRouterAuthRoute<AppUser> {
  AppRoutes(this.session);
  final ValueNotifier<AppUser?> session;

  @override
  AppUser? get user => session.value;

  @override
  Listenable get refreshListenable => session;

  @override
  List<String> get publicRoutes => ['/about'];

  @override
  List<RouteBase> get routes => [
    GoRoute(path: '/', builder: (context, state) => const Text('Home')),
    GoRoute(path: '/login', builder: (context, state) => const Text('Sign in')),
    GoRoute(path: '/signup', builder: (context, state) => const Text('Sign up')),
    GoRoute(path: '/about', builder: (context, state) => const Text('About')),
  ];
}

void main() {
  final session = ValueNotifier<AppUser?>(null);
  final service = AppRoutes(session);
  final router = service.routerConfig;
  runApp(MaterialApp.router(routerConfig: router));
}
```

Replace the example screens and connect your auth service's `onUserChanged` to the notifier. Setting a user in some unrelated service does not itself refresh GoRouter. Use `refreshListenable` or explicitly refresh your retained router when auth state changes.

The `routerConfig` getter constructs a **new** `GoRouter` on every access. Retain one configuration rather than calling it repeatedly from `build`; dispose owned routers/notifiers when their lifecycle ends. Navigation remains GoRouter's API (`go`, `push`, `pop`, and typed routes).

## Defaults

| Property | Default |
| --- | --- |
| `initialRoute` | `/` |
| `signInRoute` | `/login` |
| `signUpRoute` | `/signup` |
| `authTriggerRoutes` | Both `signInRoute` and `signUpRoute` |
| `defaultAuthRoute` | `/` |
| `publicRoutes` | Empty list |
| `debugRoute` | `/butterfly-debug` |
| `debugScreen` | null |
| `debugRoutes` | Empty list |
| `observers`, `errorBuilder`, `refreshListenable` | null |

There is no `requiresAuth` switch in the implementation. Use the non-auth base class when guards are unwanted. Auth-trigger and public-route membership uses exact `state.matchedLocation` matches, not prefixes or wildcard patterns.

## Redirect order

The auth router performs these checks in order:

1. Log and call `onRouteChanged(context, state)`.
2. Consume and clear a non-null `redirectOverride`, before auth checks.
3. If `debugScreen` is non-null, permit the debug route and allowed `debugRoutes`; redirect all other locations to the debug route.
4. For a signed-out user on a protected location, save the full URI in `postSignInRedirect` and return `signInRoute`.
5. For a signed-in user on an auth-trigger route, consume the saved URI or return `defaultAuthRoute`.
6. Permit an auth-trigger route while signed out.
7. For a signed-in user elsewhere with a saved URI, consume it.
8. For other signed-in requests, call `roleBasedRedirect(user, state)`; otherwise allow navigation.

A signed-out public or auth-trigger route does not consume the saved destination. The saved URI includes query and fragment. `temporaryRedirect` remains a deprecated getter/setter alias for `postSignInRedirect`; it is not separate state.

The non-auth `GoRouterService` only logs, invokes `onRouteChanged`, and consumes `redirectOverride`. It does not implement the auth guard sequence.

## Debug and security boundaries

`debugScreen` adds a route through `accumulatedRoutes`. In the auth router, its redirect bypass is **not** gated by `kDebugMode`; only logging is. Leave it null in production. `debugRoutes` checks both full route pattern and matched location.

`redirectOverride` is a one-use override on any route, not only the initial route, and takes precedence over guards. These client-side redirects are navigation conveniences, not backend authorization. Enforce permissions in your API or data rules.

## Core integration

`RouteServiceMixin` lives in `package:core_management/mixins/router_service.dart`. `GoRouterServiceMixin` lives in `package:core_management_route_go_router/router_service_mixin.dart`. Both expose a route service through a `BaseCoreService` subclass; neither creates an auth listener for you. The GoRouter mixin's `routerConfig` also delegates to the fresh-router getter, so the same caching guidance applies.

Implementation: `packages/core_management/lib/services/base_route.dart`, `lib/mixins/auth_route.dart`, and `packages/core_management_route_go_router/lib/`.
