description: Use synchronous in-memory acquisition and release without assuming distributed-lock guarantees.

## Guard an operation

`CoreLockService.acquire` and `release` return `bool` synchronously. There is no `runLocked`, `unlock`, or `unlockAll` method, and callers do not share a result `Future` automatically.

```dart
import 'package:core_management/services/core_lock.dart';

final locks = CoreLockService();

Future<bool> saveOnce(Future<void> Function() save) async {
  if (!locks.acquire('save-profile')) return false;
  try {
    await save();
    return true;
  } finally {
    locks.release('save-profile');
  }
}
```

Use this only when the operation fits within the lock duration and all participants share the same isolate. It is not a substitute for server-side idempotency or database transactions.

## API

| Member | Behavior |
| --- | --- |
| `CoreLockService({persistence, defaultLockDuration, pollingInterval})` | Default duration is 30 seconds; a supplied nonpositive polling interval is rejected |
| `acquire(key, {timeout, lockDuration})` | Attempts to acquire an in-memory lock until its expiry |
| `release(key)` | Removes the in-memory lock, returning whether it existed |
| `isLocked(key)` | Checks memory and removes an expired entry |
| `getLockExpiry(key)` | Returns a live in-memory expiry or null |
| `cleanupExpiredLocks()` | Removes expired in-memory entries |
| `cleanupExpiredLocksAsync()` | Cleans memory, then delegates persistence cleanup |
| `dispose()` | Clears shared in-memory state and disposes this instance's persistence |

The lock map and release-controller map are static, so instances in one isolate share them. Disposing one instance affects all those instances. There is no owner token or lease renewal: if an operation outlives its expiry, another caller can acquire the same key, and the first caller's later `release` can remove that newer lock.

## Persistence contract

Import `package:core_management/repositories/lock.dart` to implement `LockPersistence`:

| Method | Return type |
| --- | --- |
| `createOrUpdateLock(String key, DateTime expiryTime)` | `FutureOr<void>` |
| `getLockExpiry(String key)` | `FutureOr<DateTime?>` |
| `deleteLock(String key)` | `FutureOr<bool>` |
| `watchLockRelease(String key)` | `Stream<void>?` |
| `cleanupExpiredLocks()` | `FutureOr<void>` |
| `dispose()` | `void` |

Acquire/release mirror changes to persistence in background microtasks, with errors printed rather than propagated. Acquisition does not atomically consult the persistent store, so adding a backend does not make this a reliable distributed lock or restore prior locks after restart.

## Avoid timed waiting in the current implementation

A contended `acquire` with a positive `timeout` enters a synchronous waiting path. Without a watch stream, it busy-waits and blocks the isolate. With a watch stream, it sets up asynchronous work but returns `false` without awaiting acquisition. The constructor's positive `pollingInterval` is not retained or used to pace that path.

Prefer immediate acquisition and handle `false` in your application. Despite mentions in source comments, `isLockedAsync` and `getLockExpiryAsync` are not implemented methods.

Implementation: `packages/core_management/lib/services/core_lock.dart` and `lib/repositories/lock.dart`.
