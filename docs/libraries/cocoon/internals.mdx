This page documents the storage contract `cocoon_generator` emits against —
and the design decisions behind it. You only need it when writing an adapter
by hand or reasoning about on-disk data.

## Why SQLite, and why not one file per document

- **SQLite through `sqlite_async`** gives one writer plus reader isolates,
  WAL, and real transactions — everything Cocoon's guarantees hang off.
  Everything goes through a small internal executor interface
  (`CocoonExecutor`), so swapping executors (raw `package:sqlite3`, or a web
  executor later) touches one file.
- **One table per collection model**, not one per parent instance and not
  one shared `docs` table: `accounts/a1/txns/t1` and `accounts/a2/txns/t5`
  both live in the `txns` table. Wins: change notifications scoped per
  collection, no sparse columns, no `collection` column in every index, and
  per-table planner statistics.
- A file-per-document store (Hive-box style) cannot answer "all txns of
  account a1, newest first" without loading the world into RAM; SQLite
  answers it with an index range scan and stays bounded.

## Table shape

One table per collection model, named `snake_case(model)` (`Txn` → `txn`;
`sqlite_` and `_cocoon` prefixes are refused). The example below is the
`txns` table of `accounts/{accountId}/txns`:

```sql
CREATE TABLE txn (
  id TEXT NOT NULL,            -- the document id
  p_account_id TEXT NOT NULL,  -- one per path param
  data BLOB NOT NULL,          -- canonical wire bytes
  f_booked_on INTEGER NOT NULL
    CHECK (typeof(f_booked_on) = 'integer'),  -- one per FieldColumn
  f_memo TEXT CHECK (f_memo IS NULL OR typeof(f_memo) = 'text')
)
```

- **A document's identity is its scope key**: the `p_` param columns plus
  `id`, unique together through the table's scope index. There is **no
  stored `path` column** — the full path is derived from the scope key (one
  shared helper, tested round-trip both ways), which is what `DocRef.path`,
  snapshots, the cache keys, the watch keys and the change-log rows carry.
  A cascade delete keys child-table rows by their leading param columns
  (`p_account_id = 'a1'` for everything under `accounts/a1`), in the same
  transaction.
- **Files upgrade themselves.** The layout is versioned in `_cocoon_meta`
  (`format_version`): a file written before the path column was dropped is
  rebuilt table by table (new table, `INSERT ... SELECT`, drop, rename,
  indexes recreated) inside the first open that touches it — crash-safe, a
  failure leaves the old layout and the next open finishes — and a file
  written by a NEWER format refuses to open with
  `StorageFormatTooNewException`. The same rule backs up and restore: an
  older-format backup restores fine and migrates at the next open. The
  dropped tables' pages stay on the freelist until reclaimed, so an
  upgrading open that finds more than a fifth of the file free runs one
  `VACUUM` after its transaction commits (`CocoonOptions.compactAfterUpgrade`,
  default on; `onCompactionFailed` reports a failure — a full disk — without
  failing the open). Normal opens never compact.
- **Path params are typed columns** (`p_account_id`). Querying one parent is
  an index range scan; skipping the parent filter is a collection-group
  query for free.
- **Indexed fields are copied into real typed columns at write time**
  (`f_`-prefixed). SQLite can't look inside the blob; real columns are
  better than JSON generated columns: real integers, no silent
  REAL-vs-INTEGER drift, real indexes. `integer`/`real`/`text` columns carry
  a `typeof` CHECK (NULL allowed when the field is nullable); blob columns
  are unchecked. A `@Mirrored()` field gets the same column with no index
  over it (aggregates and group-by read the column; filters and sorts still
  follow the index rule). The DevTools schema view labels such columns
  "mirrored (no index)".
- **Large binaries** (receipts, statements) stay as files; documents store
  paths.
- **No in-memory copy of the database.** A bounded LRU cache of recently
  read documents (`CocoonOptions.cacheSize`, default 2000) gives Hive-like
  hot reads while RAM stays capped.

## Indexes

- Every table gets an implicit `UNIQUE` index over `(p_params..., id)` —
  `cx_<table>_scope` — which serves "list a parent's docs by id" and scoped
  queries.
- Declared indexes become `CREATE [UNIQUE] INDEX cx_<table>_<16hex>`, where
  the hex fingerprints the canonical definition; the doc id is appended as
  the final part with the direction of the last declared part.
- A `unique` index is the exception: it never gets the id (otherwise the
  constraint could never fire), and it is unique across the whole collection
  group, so add the path param (e.g. `Index(['accountId', 'ref'],
  unique: true)`) to make it unique per parent.
- **Reconcile on open** runs in one write transaction: create missing
  tables; add missing `f_` columns and backfill them by decoding every row
  with the adapter in batches of 500 (keyed by the scope key, scanned in
  rowid order); drop undeclared `f_` columns (their indexes go first);
  create missing and drop stale `cx_` indexes. A per-table shape hash in
  `_cocoon_meta` makes a no-change open do no DDL at all. Tables without a
  registered adapter are never touched (but they do take part in the
  storage-format upgrade, which rebuilds any table still carrying the old
  `path` column).
- SQLite cannot add a `NOT NULL` column to a table with rows, so backfilled
  columns are declared nullable and the adapter's non-null invariant is
  enforced at write time.

## Many documents by id

`db.getAll(refs)` — the user-facing behaviour and its measured numbers are
on [Bulk Loads & Batch Reads](/libraries/cocoon/bulk) — answers from the
bounded cache where it can; only the
misses reach SQLite, grouped per collection table and fetched in chunks of
500 scope keys, with every chunk of one call inside one `BEGIN IMMEDIATE`
read transaction on a reader connection — one consistent snapshot, one
round trip per table per chunk (`BEGIN` + statements + `END` over
sqlite_async's reader isolate). A subcollection keys by its full scope key
with row values, the same shape the batch `update` existence check uses; a
root collection keys by `id` alone:

```sql
-- accounts/{accountId}/txns, chunk of 500 refs:
SELECT p_account_id, id, data FROM txn
WHERE (p_account_id, id) IN (VALUES (?, ?), (?, ?) /* ... 500 tuples */)

-- accounts (no path params):
SELECT id, data FROM account WHERE id IN (?, ? /* ... 500 */)
```

Rows map back to their positions through the derived full path (the same
one scope-key helper every other path consumer uses), decode per document,
and populate the cache exactly like `get()` does. Missing documents are
simply absent from the answer: `null` at their positions. The chunk size
(500) is measured, not guessed — `benchmarks/cocoon_rivals/GETALL.md` has
the table and the breakdown of where the remaining time goes (isolate
round trips, not SQL).

## Canonical protobuf wire format

The document body (`data`) is a protobuf blob encoded canonically by the
generated codec (`WireWriter`): the same document always yields the same
bytes, which is what lets watches deduplicate emissions by byte equality and
a journal chain hash documents directly.

Canonical means:

- fields are written in ascending field-number order (anything else throws);
- unknown fields are never carried over;
- the caller decides presence: non-null values are written, nulls skipped.

The generated codecs map Dart types to wire encodings like this:

| Dart type | Wire encoding |
| --- | --- |
| `int`, `DateTime` (UTC microseconds) | zigzag varint (`sint64`) |
| `bool` | varint `0`/`1` |
| `double` | little-endian IEEE 754 (`double`, wire type i64) |
| `String`, enum (by name) | UTF-8, length-delimited |
| `Uint8List` | length-delimited bytes |
| `List<T>` / `@Embedded` value | nested length-delimited message |

Missing fields decode to the constructor default, else `null` when
nullable, else the zero value — so documents written before a field existed
still load. Unknown field numbers from the future are skipped (`reader.skip`),
which is what makes old readers tolerant of newer writers.

The canonical layout is also what makes migration rewrites safe to do at
the wire level: the engine's migration runner rebuilds each document's
bytes field by field, and a **backfill** (the migrate command's answer to a
newly added required field) is the same operation where the field does not
exist yet — every occurrence of the field is dropped and the stub's value
is inserted at its canonical ascending position. The stub receives the
decoded document; the value it returns is encoded with the field's normal
wire encoding (`DateTime` as UTC microseconds, enums by name).

## Internal tables

Cocoon keeps three internal tables (all reserved-name prefixed):

```sql
-- key/value metadata: schema_version, per-table shape hashes
CREATE TABLE _cocoon_meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);

-- the change log: one row per touched document per committed write
CREATE TABLE _cocoon_changes (
  seq INTEGER PRIMARY KEY AUTOINCREMENT,
  tbl TEXT NOT NULL,
  path TEXT NOT NULL,
  op TEXT NOT NULL CHECK (op IN ('set','delete')),
  at INTEGER NOT NULL
);

-- deferred bulk-load indexes: one row per secondary index a running
-- BulkWriter has dropped, with the DDL that recreates it
CREATE TABLE _cocoon_bulk (tbl TEXT NOT NULL, index_name TEXT NOT NULL, sql TEXT NOT NULL)
```

### How bulk-index deferral works

The behaviour an app sees — what waits, what runs, crash recovery — is on
[Bulk Loads & Batch Reads](/libraries/cocoon/bulk); this is the mechanism.
A `BulkWriter` load with the default `deferIndexes: true` skips secondary
index maintenance while it runs. On the first chunk that touches a table,
inside the same write transaction as the chunk's rows, the writer decides —
the table is empty, or the writer has buffered more rows for the table than
the table holds — and, when deferral pays:

1. inserts one `_cocoon_bulk` row per declared secondary index, carrying
   the exact `CREATE ... INDEX IF NOT EXISTS` statement (the scope index is
   never touched), and
2. `DROP INDEX`es each of them.

The writes of the chunk commit atomically with the drops, so the meta rows
on disk always match the physically missing indexes. Every committed chunk
still appends its change-log rows and fires its watch event; the
hot-document cache works as always.

While the indexes are deferred, a query whose plan needs one of them (the
planner's serving index, exposed as `PlannedQuery.servingIndex`) is held by
the engine until the writer closes; queries served by the scope index,
`.allowFullScan()` queries and `get()` by id run immediately.

`close()` rebuilds exactly the indexes the writer dropped — one write
transaction: `CREATE INDEX` per index, then the meta rows deleted. A crash
mid-load leaves the rows behind with the indexes gone (the table's shape
hash is unchanged, so the reconciler would not recreate them); `Cocoon.open`
runs the recovery inside its open transaction: every recorded index still
declared by the current schema and living on an existing table is recreated
from its recorded DDL, then all rows are deleted. An index the app no longer
declares is not resurrected — the reconciler's decision wins.

### How backups and restores move files

The API and what the app owns vs what the engine owns are on
[Backup & Restore](/libraries/cocoon/backup); this is the file protocol.
`db.backupTo()` runs SQLite's `VACUUM INTO` against the source file inside
`Isolate.run` (raw connections in `sqlite_executor.dart`, the only file that
imports the SQLite packages): the statement takes one read snapshot of the
database and writes a fresh, compacted, single-file copy in
rollback-journal mode — the open database and its WAL are untouched, which
is what makes the copy consistent while writers keep committing. The copy
lands at `<path>.partial` (a leftover from a crashed backup is removed
first), is fsynced, then stamped in its `_cocoon_meta`: the backup format
version, the created-at in UTC microseconds, the copy's own change-log head
(as `backup_last_change_seq`) and the Cocoon version. Stamping also replaces
the instance id with a throwaway, so a backup never carries the source's
identity. The stamped file is renamed onto `path`; a failure anywhere before
the rename deletes the partial, so `path` never holds a half-written backup.

`Cocoon.inspectBackup()` opens the file on a raw connection:
`PRAGMA integrity_check` first, then the `_cocoon_meta` rows. The typed
errors separate "not ours" (`NotCocoonBackupException` — no `_cocoon_meta`,
or no backup marker; a live Cocoon database file reports this too), "broken"
(`BackupDamagedException` — failed integrity check, unreadable bytes, or a
metadata row that does not parse) and "newer app"
(`BackupFormatTooNewException` — an unknown backup format version).

`Cocoon.restoreBackup()` refuses while any `Cocoon` in the isolate holds the
target open (open/close register the absolute paths), validates the backup,
and applies `open`'s schema rule to its stored `schema_version` BEFORE
touching the target — a newer schema refuses, an older one migrates at the
next open. Only then do files move: copy to `<path>.restoring` + fsync,
re-roll the copy's instance id (a restored database is a new instance),
move the current database with its `-wal`/`-journal` sidecars to
`<path>.before-restore` (the `-shm` is a rebuildable index over the WAL and
is dropped), delete any sidecars left at the target path, rename the copy
onto the target, fsync. Every step has a failure-injection seam
(`BackupOperations.debugFailBeforeStep`, test-only); a failure at any step
undoes the steps before it — the original database ends the run where it
started.

## Money guidance

Cocoon stores integers exactly — use that for money:

- store amounts as `int` **minor units** (cents, sen) plus an ISO 4217
  currency code field; the generator writes ints as zigzag `sint64` and
  indexes them as SQLite `INTEGER`;
- `SUM` over integer columns is exact and throws on overflow;
- **never** `TOTAL()` or `AVG()` for money — they return REAL;
- never sum across currencies; convert first, then sum.

## Aggregates

`query.aggregate([...])` and `query.groupBy([...])` compute in SQLite over
the mirrored `f_` columns — the app-facing API, semantics and measured
numbers are on [Aggregates & Group By](/libraries/cocoon/aggregates). The
document blob is never decoded, and one
`get()` is exactly one read statement. The filters are planned by the same
code as `get()`: same index rule, same `MissingIndexException`, same
`.allowFullScan()`, and the same wait when a bulk writer has the serving
index deferred.

The count statement is the plain aggregate shape — `query.count()` is
`aggregate([count()])`:

```sql
SELECT count(*) AS c, COALESCE(SUM(f_amount_minor), 0) AS a0,
       AVG(f_rate) AS a1
FROM txn WHERE p_account_id = ? AND f_status = ?
```

- `sum` of an integer column is `COALESCE(SUM(col), 0)`: never null, exact,
  and an overflow past ±2^63 aborts the statement — surfaced as
  `AggregateOverflowException`, never as a wrapped value. A real column
  coalesces to `0.0`.
- `average` is plain `AVG`: always REAL, `null` when no row has a value.
- nulls are skipped by `SUM`/`AVG`/`MIN`/`MAX` and counted by `count(*)`.

A query with `orderBy` + `limit` aggregates the first N rows in that order,
as a subquery (a top-level `LIMIT` would apply to the single result row and
do nothing); without a limit the `ORDER BY` is dropped:

```sql
SELECT count(*) AS c, COALESCE(SUM(f_amount_minor), 0) AS a0
FROM (SELECT f_amount_minor FROM txn
      WHERE p_account_id = ? ORDER BY f_booked_on DESC, id DESC LIMIT ?)
```

The group-by extension emits one key expression per `groupBy` key, a
`GROUP BY` over their aliases and an ascending `ORDER BY` (SQLite sorts
NULLs first, so null keys form their own first group):

```sql
SELECT (f_booked_on - (((f_booked_on % ?) + ?) % ?)) AS k0,
       count(*) AS c,
       COALESCE(SUM(f_amount_minor), 0) AS a0, MIN(f_booked_on) AS a1
FROM txn WHERE p_account_id = ?
GROUP BY k0 ORDER BY k0 ASC LIMIT ?
```

Key expressions, per key kind:

- **`key(field)` / `paramKey(param)`**: the `f_`/`p_` column itself.
- **`bucket(field, width: w)`** on an integer field with an integer width:
  `field - ((field % w) + w) % w` — floor division in pure integer
  arithmetic (no floats, correct for negative amounts). On a real field:
  `FLOOR(field / w) * w`.
- **`year`/`month`/`day(field, utcOffset:)`** on a `DateTime` column: shift
  the stored UTC microseconds by the offset, take the containing day with
  the same integer floor-mod (`floorDiv(micros + offset, 86400000000)`),
  multiply back to the local midnight's UTC seconds and read the calendar
  off it — `date(..., 'unixepoch')` plus `strftime('%Y%m')`, cast to
  INTEGER. Fixed offsets only: a DST zone would silently bucket wall-clock
  times around transitions wrong, so for those run one aggregate per period
  with range filters on the instant instead (see the `month` dartdoc).

Aggregates read only columns that exist: an `AggregateFunction` or
`GroupKeySpec` over a field without an `f_` column throws an
`UnmirroredFieldException` naming both fixes — `@Mirrored()` on the field
when you only total or group by it, an `Index([...])` when a query also
filters or sorts on it (a mirrored-only column passes the aggregate rule;
the index rule still refuses filters on it).

## Benchmarks

The storage contract above is measured in `packages/cocoon_bench` — full
tables in its `RESULTS.md` — against sembast on finance-shaped data
(10k/100k/300k txns), fresh process per run, memory reported against a
measured harness-only baseline. The engine-vs-engine comparison (drift,
Isar, ObjectBox, Hive CE, sembast) and the tuning knobs are on
[Performance](/libraries/cocoon/performance).

- **Bounded RAM, measured.** The engine's own share of RSS is flat across
  the 30x data range: indistinguishable from the bare harness right after
  open, +39 MB after reads at every size. The bounds are the ones this page
  describes — the `cacheSize` LRU (decoded documents only), SQLite's
  per-connection page cache, and a fixed pool of reader isolates. sembast
  decodes its whole log into RAM at open: +598 MB over the same floor at
  300k.
- **Cold open is flat** (~80 ms at every size): opening reads nothing until
  asked; the schema reconcile touches only metadata. sembast's open parses
  the entire log: 0.19 → 2.36 s.
- **Indexed reads** (the `cx_` index range scans): one account's latest-50
  stays ~0.7 ms p50 from 10k to 300k; sembast climbs 3.7 → 215 ms.
- **The write amplification is real**: one row per document plus one per
  index plus change-log rows, committed with an fsync at
  `Durability.full` — bulk import 1.6-2x slower than sembast's JSON-line
  appends, single writes 5-7x slower. `Durability.normal` takes back 4.2x
  of the single-write cost (fsync skipped, still crash-safe);
  `keepChanges: false` another ~11% when nothing reads the change log;
  `cacheSize` only charges RAM for documents actually read (a warm
  1,000-doc working set: 113 ms cold → 2 ms warm, and `cacheSize` 20000
  bought nothing and cost nothing over 2000).

### Against other engines

`benchmarks/cocoon_rivals` repeats the measurement against drift (plain
SQLite), Isar, ObjectBox, Hive CE and sembast — and against Cocoon itself
at `Durability.normal` — on the same finance-shaped data up to 1,000,000
transactions, with per-workload verdicts in its
[RESULTS.md][rivals-results]. The claims above survive contact with
engines that have real indexes, not just sembast:

- **Bounded RAM holds at 1M txns.** Cocoon's after-reads RSS sits at the
  bare-harness floor (431 MB); sembast is +2,242 MB over that floor,
  Hive +2,214 MB, Isar +262 MB.
- **The composite indexes win beyond latest-50.** The paged all-accounts
  month range is 320 ms at 1M vs 2,476 ms for drift's LIMIT/OFFSET paging
  (keyset cursors, not offsets) and 98,982 ms for sembast; the
  `(status, bookedOn)` search is 1.42 ms flat vs 608 ms (Hive) at 1M.
- **WAL readers keep their promise under writes.** With one committed txn
  every 10 ms, latest-50 p95 is 3.0 ms; drift serializes every statement
  through one background isolate and pays 4.96 ms.
- **Bulk writes no longer pay a round trip per document.** Writes are
  buffered and sent as one batched statement, the writer connection gets
  a bigger page cache and checkpoint interval: 1M txns import in 64.7 s
  (was 123.6 s; drift 95.5 s) and the 300k NDJSON restore takes 11.2 s
  (was 33.0 s; drift 13.9 s).
- **The write amplification is still the tax.** Isar imports 1M in
  24.9 s and Hive in 8.0 s; Hive restores 300k in 3.0 s; files are
  388 MB vs drift's 224 MB; and SQL aggregation is
  3.6x faster on the year report — the one workload a document API
  structurally cannot match.
