## Setup

Three steps, and no publish or clear code in your app:

1. Mix `RiverpodUser` into your user model.
2. Create one top-level `AuthManagementRiverpodRepository` and return it from your auth service's `providerRepo`.
3. Call `initialize(ref)` on it once from your root widget.

```dart
import 'package:auth_management/auth_management.dart';
import 'package:auth_management/auth_management_provider.dart';
import 'package:auth_management_provider_riverpod/auth_management_provider_riverpod.dart';
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

class AppUser with RiverpodUser {
  AppUser(this.name);
  final String name;
}

final riverpodProvider = AuthManagementRiverpodRepository<AppUser>();

class AuthService extends AuthServiceRepository<AppUser> {
  @override
  final dbRepo = InMemoryDatabaseRepository<AppUser>();

  @override
  AuthServiceProviderRepository<AppUser> get providerRepo => riverpodProvider;
}

final authService = AuthService();

void main() {
  authService.initialize();
  runApp(const ProviderScope(child: App()));
}

class App extends ConsumerWidget {
  const App({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    riverpodProvider.initialize(ref);
    return const MaterialApp(home: UserLabel());
  }
}

class UserLabel extends ConsumerWidget {
  const UserLabel({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final user = ref.watch(riverpodUserStateProvider) as AppUser?;
    return Text(user?.name ?? 'Signed out');
  }
}
```

Replace the in-memory cache with a persistent [storage repository](/libraries/auth/features/datasources) in a real app.

From then on, every user change from your auth service is published to `riverpodUserStateProvider`, and `signOut()` clears it. Watch the provider anywhere below `ProviderScope`.

Keep the bridge as one top-level instance, as above, so the auth service and the root widget share it. The getter must return that same instance every time; constructing a new one in the getter would leave the initialized bridge disconnected.

## How the sync works

The base `auth_management` library owns the wiring. `AuthServiceRepository.initialize()` forwards every user change to `providerRepo.sync(user)`, before calling `onUserChanged`. `sync` calls `bindUserToProvider` for a user and `clearUser` for sign-out. Both are internal: app code never calls them.

Order doesn't matter. If auth resolves before the bridge is initialized (for example, a persisted session restored in `main()`), the latest user is held and published as soon as `initialize(ref)` runs. That delivery is scheduled just after the current build, so calling `initialize` from `build` or `initState` doesn't modify a provider mid-build. Repeat calls are ignored, so calling it in `build` is fine.

Use your root widget: the bridge keeps that `WidgetRef` for the app's lifetime, and has no dispose method. A `ConsumerStatefulWidget` calling it in `initState` works the same way.

## What the provider holds

`riverpodUserStateProvider` is a keep-alive notifier holding `RiverpodUser?`, initially null. It is not an `AsyncValue` or an auth-state enum, and the package doesn't define `authStateProvider` or `currentUserProvider`. Cast to your model when reading; the provider isn't generic per app.

A nullable user can't distinguish "still restoring the session" from "signed out". If your UI needs a splash or error state, keep that in your own state alongside it.

## Other state managers

The same mechanism works for any library. Extend `AuthServiceProviderRepository<T>` from `package:auth_management/auth_management_provider.dart`, implement `bindUserToProvider`, `clearUser`, and `getUser`, and call the protected `markInitialized()` once your bridge has whatever handle it needs. Return it from `providerRepo`, and the auth service keeps it in sync.

Implementation: `packages/auth_management/lib/src/provider_repository.dart`, `repository.dart`, and `packages/auth_management_provider_riverpod/lib/src/`.
