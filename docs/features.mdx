The `butterfly` CLI (`butterfly_cli`) automates repetitive project tasks: generating model boilerplate, stamping `lib/version.dart` from `pubspec.yaml`, creating conventional commits, and exposing an MCP server for AI coding agents.

## Command overview

| Command | Shorthand / Aliases | Description |
| --- | --- | --- |
| `butterfly version` | — | Prints the CLI's built-in `kVersion` (`0.2.0`) |
| `butterfly init` | — | Interactive project wizard (see [Installation](/installation#interactive-project-scaffolding-butterfly-init)) |
| `butterfly generate model <Name>` | `gen` / `g`, `m` / `mdl` | Scaffolds a model class under `lib/models/` |
| `butterfly generate version` | `gen` / `g` | Reads `pubspec.yaml` version and writes `lib/version.dart` |
| `butterfly commit` | `c`, `comit`, `commits`, `cm` | Interactive or flag-driven conventional `git commit` |
| `butterfly mcp-server` | `mcp`, `mcp-srv` | Launches the stdio Model Context Protocol (MCP) server |

<Info>
  <Icon name="terminal" /> **Global flags:** Pass `--verbose` (`-v`) on any command for detailed logging, or `--dev` (`-D`) to rethrow caught exceptions with full stack traces instead of taking the standard exit path. There is no `butterfly generate service` subcommand.
</Info>

## Model generator (`generate model`): CLI vs. Manual Dart

<Tabs>
  <TabItem label="With Butterfly CLI" value="cli-with-butterfly">
    Run inside any project containing `pubspec.yaml` and `lib/` to scaffold `json_serializable` or `built_value` models in one command:

    ```bash
    # Default: mutable model with json_serializable hooks
    butterfly generate model Booking

    # Nested path -> writes lib/models/auth/user.dart with class AuthUser
    butterfly g m AuthUser --path auth

    # Plain Dart class without JSON serialization
    butterfly generate model Settings --no-serializable

    # Immutable built_value model
    butterfly generate model Invoice --immutable
    ```

    Then add your fields and run `dart run build_runner build`.
  </TabItem>
  <TabItem label="Without Butterfly CLI (Manual Model)" value="cli-without-butterfly">
    The CLI only writes standard Dart source files—it adds **zero runtime dependency** on Butterfly. If you prefer not to use the CLI, create `lib/models/booking.dart` by hand with `@JsonSerializable()`:

    ```dart title="lib/models/booking.dart (suggested)"
    import 'dart:convert';
    import 'package:json_annotation/json_annotation.dart';

    part 'booking.g.dart';

    @JsonSerializable()
    class Booking {
      const Booking({required this.id});
      final String id;

      factory Booking.fromJson(Map<String, dynamic> json) =>
          _$BookingFromJson(json);

      Map<String, dynamic> toJson() => _$BookingToJson(this);

      factory Booking.fromJsonRaw(String rawJson) =>
          Booking.fromJson(jsonDecode(rawJson) as Map<String, dynamic>);

      String toJsonRaw() => jsonEncode(toJson());
    }
    ```
  </TabItem>
</Tabs>

### Generator flags

<Property name="--serializable / -s" type="boolean" optional>
  Defaults to `true`. Generates `fromJson`, `toJson`, `fromJsonRaw`, and `toJsonRaw` helpers. Pass `--no-serializable` for a plain class without JSON hooks.
</Property>

---

<Property name="--immutable / -i" type="boolean" optional>
  Defaults to `false`. Switches from the standard mutable class brick to the `built_value` abstract class template.
</Property>

---

<Property name="--path / -p" type="string" optional>
  Optional subdirectory inside `lib/models/`. Class names are converted to `PascalCase` while file and folder names use `snake_case`. If the model name ends with the folder name (such as `AuthUser` with `--path auth`), the redundant prefix is stripped from the filename (`lib/models/auth/user.dart`) while keeping `class AuthUser`. Passing a model name identical to `--path` is rejected.
</Property>

### Completing generated models

The CLI scaffolds the skeleton file (and prompts before overwriting an existing file), but **you add the fields, dependencies, and codegen run**:

<Tabs>
  <TabItem label="Standard (@JsonSerializable)" value="json-model">
    1. Add `json_annotation` plus dev dependencies `json_serializable` and `build_runner`:
       ```bash
       flutter pub add json_annotation dev:json_serializable dev:build_runner
       ```
    2. Add your fields and constructor parameters to the generated class.
    3. Generate the `.g.dart` part:
       ```bash
       dart run build_runner build
       ```
  </TabItem>
  <TabItem label="Immutable (built_value)" value="built-value-model">
    1. Add `built_value` plus dev dependencies `built_value_generator` and `build_runner`:
       ```bash
       flutter pub add built_value dev:built_value_generator dev:build_runner
       ```
    2. Define your getters inside the abstract class.
    3. **If `--serializable` is enabled (the default):** The template references a project-level `serializers` instance (`serializers.deserializeWith(...)`). Create and import your app's `@SerializersFor([...])` registry (with `StandardJsonPlugin` if using map JSON) before running `build_runner`, otherwise the newly generated file will not compile yet.
  </TabItem>
</Tabs>

## Stamp app version (`generate version`)

Keep an in-app constant synced with your `pubspec.yaml` version string:

```bash
butterfly generate version
```

This reads `version:` from your project's `pubspec.yaml` and writes `const String kVersion = '...';` into `lib/version.dart`.

<Warning>
  `butterfly generate version` overwrites `lib/version.dart` immediately without confirmation. Check `lib/version.dart` first if you keep custom code in that file.
</Warning>

## Conventional commits (`butterfly commit`)

Create a formatted conventional commit (`<action>: <message>`) from the terminal:

```bash
butterfly commit -a feat -m "add credit facility model"
```

- **Supported `--action` (`-a`) types:** `fix`, `feat`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`.
- **Interactive fallback:** Omit `-a` or `-m` and the CLI prompts you in the terminal.
- **Staging behavior:** `butterfly commit` executes a real `git commit -m`. If `git status` reports `"no changes added to commit"`, the CLI asks whether to stage all changes (defaulting to **Yes**) and runs `git add .`. Stage specific files manually beforehand if you have unrelated edits in your working tree.

## MCP server (`butterfly mcp-server`)

Start the stdio Model Context Protocol server for AI assistants:

```bash
butterfly mcp-server
```

<Property name="test" type="MCP tool" optional>
  Accepts an optional `message` string and echoes it back to verify MCP connectivity. Does not run `dart test`.
</Property>

---

<Property name="init" type="MCP tool" optional>
  Initializes a project non-interactively. Parameters:
  - `useCore` (`bool`, default `true`)
  - `useAuth` (`bool`, default `false`) — requires `userModelName` when `true`
  - `useRouter` (`bool`, default `false`) — `routerType` defaults to `goRouter`

  Writes `.butterfly_project.yaml` (version `0.0.0`) and restores the project root directory between steps.
</Property>

---

<Property name="generate_model" type="MCP tool" required>
  Scaffolds a model via MCP. Requires `name` (`String`), with optional `serializable` (`true`), `immutable` (`false`), and `path`. Unlike interactive CLI runs, `generate_model` refuses to overwrite an existing target file.
</Property>
