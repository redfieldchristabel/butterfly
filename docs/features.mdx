## Commands

| Command | Aliases | Effect |
| --- | --- | --- |
| `butterfly version` | None | Prints the CLI's `kVersion` constant |
| `butterfly init` | None | Interactive project scaffolding |
| `butterfly generate model <Name>` | `generate`: `gen`, `g`; `model`: `m`, `mdl` | Generates a model skeleton |
| `butterfly generate version` | `generate`: `gen`, `g` | Writes `lib/version.dart` |
| `butterfly commit` | `c`, `comit`, `commits`, `cm` | Invokes Git to create a conventional commit |
| `butterfly mcp-server` | `mcp`, `mcp-srv` | Starts the stdio MCP server |

There is no `generate service` command. Use [installation](/installation) for initialization behavior and known template limitations.

Global flags are `--verbose` / `-v` and `--dev` / `-D`. The verbose flag requests verbose logging; the dev flag rethrows errors handled inside the guarded command execution rather than taking the normal error exit path.

## Generate a model

Run inside a project with both `pubspec.yaml` and `lib/`:

```bash
butterfly generate model Booking
butterfly g m AuthUser --path auth
butterfly generate model Settings --no-serializable
butterfly generate model Invoice --immutable
```

| Option | Default | Meaning |
| --- | --- | --- |
| `--serializable`, `-s` | `true` | Include serialization support; disable with `--no-serializable` |
| `--immutable`, `-i` | `false` | Use the `built_value` template instead of the plain model template |
| `--path`, `-p` | No subdirectory | Subdirectory under `lib/models/` |

The name becomes PascalCase; file and directory names become snake_case. `AuthUser --path auth` produces `lib/models/auth/user.dart` while keeping class name `AuthUser`. A class name identical to the path is rejected. Existing target files trigger an overwrite prompt in the CLI; declining skips generation.

The generator creates an empty model skeleton. Add fields and constructor parameters yourself. It does not install serialization dependencies or run `build_runner`.

### Plain serializable models

Add `json_annotation`, plus development dependencies `json_serializable` and `build_runner`, to your consuming project. After editing fields, run:

```bash
dart run build_runner build
```

The template includes `fromJson`, `toJson`, `fromJsonRaw`, and `toJsonRaw`. Without serialization it creates only the plain class and constructor.

### Immutable models

Add `built_value` and development dependencies `built_value_generator` and `build_runner`. The template uses Flutter's `@immutable` annotation and always references a generated `.g.dart` part.

With serialization enabled, the template also references an application-owned `serializers` registry without generating or importing one. Define that registry, register the model's serializer, configure map-shaped JSON serialization as needed, and import it before running generation. Do not treat the generated immutable file as immediately compilable.

## Generate a version file

```bash
butterfly generate version
```

Reads the project's pubspec version and writes a single `const String kVersion` declaration to `lib/version.dart`. It overwrites that file without an overwrite prompt; inspect existing content first. This is different from `butterfly version`, which prints the CLI's own version constant.

## Conventional commits

`butterfly commit` is a write operation, not a message preview. It runs `git commit -m` after collecting the action and message.

`--action` / `-a` accepts `fix`, `feat`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, or `chore`. `--message` / `-m` supplies the subject text. Missing values are prompted for.

If human-readable `git status` contains `no changes added to commit`, the command asks whether to stage changes, defaulting to yes, then uses `git add .`. That detection depends on Git's output wording. Review and stage only intended files yourself before invoking the command. It does not push, and it does not provide separate scope, body, or breaking-change flags.

## MCP server

```bash
butterfly mcp-server
```

The server registers three tools:

| Tool | Inputs and behavior |
| --- | --- |
| `test` | Optional `message`; echoes text, not a test-suite runner |
| `init` | `useCore` defaults true; `useAuth` and `useRouter` default false; `userModelName` is required when auth is selected; router type defaults to `goRouter` when enabled |
| `generate_model` | Required `name`; optional `serializable` (true), `immutable` (false), and `path` |

MCP `init` saves `.butterfly_project.yaml` with configuration version `0.0.0` and restores the project root before generating services. Unlike interactive `init`, it does not explicitly create all four organizational directories. Dependency installation can still prompt. `generate_model` rejects an existing file instead of asking to overwrite it.

These are the registered tools, not a promise of fully unattended operation or compatibility with every MCP client. Project tools depend on the server's working directory, and command logging should be checked for stdio-protocol compatibility in your client.

## Verification

The workspace's declared analyzer script is:

```bash
dart run melos run analyze --no-select
```

The CI workflow analyzes and tests the CLI:

```bash
cd butterfly_cli
dart analyze
dart test
```

For a Flutter package, run `flutter test --no-pub` in that package after dependencies are resolved. Some checked-in tests are placeholders; a green run is not evidence that every provider, platform, or scaffold works.

Validate the documentation separately from the repository root:

```bash
npx --yes @docs.page/cli@latest check
```

See the [official docs.page CLI reference](https://use.docs.page/reference/cli) for local preview and individual validation flags. Documentation checks validate rendering, metadata, links, and assets, not Dart examples or authentication behavior.
