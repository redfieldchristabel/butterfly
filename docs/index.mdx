Butterfly is a **modular, ejectable toolkit of Flutter packages and a Dart CLI**, not a rigid lock-in framework. Every package removes repetitive plumbing while keeping your domain models and widgets clean—and every page in these docs shows both the **With Butterfly** setup and the **Without Butterfly (Raw Flutter)** equivalent so you can adopt or eject any piece at any time.

<Info>
  <Icon name="shield-halved" /> **Zero Lock-In Guarantee:** If you ever outgrow a Butterfly package or want to drop the dependency, every feature maps directly to standard Flutter, `go_router`, `flutter_riverpod`, or database primitives. You just trade Butterfly's concise glue for the raw boilerplate shown in the second tab of each guide.
</Info>

## How the pieces fit together

Butterfly separates your app into clean, replaceable layers so your UI never talks directly to raw storage or third-party auth SDKs:

<Tabs>
  <TabItem label="Authentication flow" value="auth-flow">
    1. <Icon name="id-card" /> **External Identity (`IdentityAuthRepository`):** Watches Firebase Auth or an OAuth2 session.
    2. <Icon name="user-check" /> **Profile Resolution (`fetchUser`):** Maps that raw identity to your own `AppUser` domain model.
    3. <Icon name="database" /> **Local Cache (`dbRepo`):** Persists `AppUser` in Sembast, Hive CE, Isar, or memory so repeat startups resolve without unnecessary network calls.
    4. <Icon name="bolt" /> **State Bridge (`providerRepo`):** Automatically pushes every user emission and sign-out event into Riverpod (`userProvider`) or your custom state adapter.
  </TabItem>
  <TabItem label="Core & routing flow" value="core-flow">
    1. <Icon name="bug-slash" /> **App Bootstrap (`BaseCoreService`):** Installs `FlutterError.onError` and `PlatformDispatcher.instance.onError` hooks before `runApp`.
    2. <Icon name="palette" /> **Theme & Typography (`BaseThemeService`):** Builds a seeded Material 3 `ColorScheme` and exposes typed `CoreTypographyTheme` styles.
    3. <Icon name="signs-post" /> **Auth-Aware Routing (`GoRouterAuthRoute`):** Evaluates route guards in a strict 8-step sequence, saving blocked deep links in `postSignInRedirect` and replaying them once signed in.
  </TabItem>
  <TabItem label="Zero lock-in (Ejectability)" value="ejectability">
    Why teams hesitate to adopt utility libraries is fear of abandonment. Butterfly solves this in three ways:
    - **You own the classes:** You subclass `BaseCoreService` or `AuthServiceRepository<AppUser>` in your own `lib/services/` folder.
    - **Pure domain models:** `AppUser` is your own class; `RiverpodUser` and `FirebaseUser` are tiny mixins you can remove in seconds.
    - **Side-by-side escape hatches:** Every guide on this site includes a **Without Butterfly** tab with working, analyzable Dart code showing the exact raw implementation.
  </TabItem>
</Tabs>

## Design principles & adoption rules

<AccordionGroup>
  <Accordion defaultOpen title="You own the concrete service classes">
    Butterfly does not lock you into hidden static singletons like `AuthService.signIn()`. Instead, you subclass `BaseCoreService` or `AuthServiceRepository<AppUser>` in your own project, wire only the adapters you want, and expose your own instance.
  </Accordion>
  <Accordion title="Explicit, tree-shakeable utility imports">
    The main `package:core_management/core_management.dart` barrel exports the core service base classes (`BaseCoreService`, `BaseThemeService`, `BaseErrorHandlerService`, `BaseLoadingService`, `BaseRouteService`). Standalone utilities such as `HexColor`, `ScreenLayout`, `TaskQueueMixin`, `CoreLockService`, and `LoadingOverlay` use dedicated sub-imports so you always see what a file depends on.
  </Accordion>
