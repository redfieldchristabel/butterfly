Butterfly is a **modular toolkit of Flutter packages and a Dart CLI**, not a rigid monolithic framework. Pull in a single package for GoRouter authentication redirects, wire up zero-boilerplate Riverpod user state, or use the CLI to scaffold `built_value` and `json_serializable` models.

  **Ground-truth documentation:** Every guide and code block on this site is verified directly against the current repository source code and compiler—including honest callouts where packages have sharp edges or unfinished wiring.
</Info>

## How the pieces fit together

Butterfly separates your app into clean, replaceable layers so your UI never talks directly to raw storage or third-party auth SDKs:

<Tabs>
  <TabItem label="Authentication flow" value="auth-flow">
    1. **External Identity (`IdentityAuthRepository`):** Watches Firebase Auth or an OAuth2 session.
    2. **Profile Resolution (`fetchUser`):** Maps that raw identity to your own `AppUser` domain model.
    3. **Local Cache (`dbRepo`):** Persists `AppUser` in Sembast, Hive CE, Isar, or memory so repeat startups resolve without unnecessary network calls.
    4. **State Bridge (`providerRepo`):** Automatically pushes every user emission and sign-out event into Riverpod (`userProvider`) or your custom state adapter.
  </TabItem>
  <TabItem label="Core & routing flow" value="core-flow">
    1. **App Bootstrap (`BaseCoreService`):** Installs `FlutterError.onError` and `PlatformDispatcher.instance.onError` hooks before `runApp`.
    2. **Theme & Typography (`BaseThemeService`):** Builds a seeded Material 3 `ColorScheme` and exposes typed `CoreTypographyTheme` styles.
    3. **Auth-Aware Routing (`GoRouterAuthRoute`):** Evaluates route guards in a strict 8-step sequence, saving blocked deep links in `postSignInRedirect` and replaying them once signed in.
  </TabItem>
  <TabItem label="Project conventions" value="conventions">
    When you scaffold with `butterfly init`, files are organized under `lib/`:
    - `lib/models/` — Domain models (`AppUser`, generated `.g.dart` parts)
    - `lib/services/` — App singletons (`CoreService`, `ThemeService`, `AuthService`, `RouteService`)
    - `lib/screens/` — Top-level route destinations
    - `lib/widgets/` — Reusable UI components

    These folders are a helpful convention, not a requirement enforced by the runtime packages.
  </TabItem>
</Tabs>

## Package catalog

| Package | Role | Key Exports |
| --- | --- | --- |
| `butterfly_cli` | CLI & Mason scaffolding | `butterfly` executable (`init`, `generate`, `commit`, `mcp-server`) |

## Design principles & adoption rules

<AccordionGroup>
  <Accordion defaultOpen title="You own the concrete service classes">
    Butterfly does not lock you into hidden static singletons like `AuthService.signIn()`. Instead, you subclass `BaseCoreService` or `AuthServiceRepository<AppUser>` in your own project, wire only the adapters you want, and expose your own instance.
  </Accordion>
  <Accordion title="Explicit, tree-shakeable utility imports">
    The main `package:core_management/core_management.dart` barrel exports the core service base classes (`BaseCoreService`, `BaseThemeService`, `BaseErrorHandlerService`, `BaseLoadingService`, `BaseRouteService`). Standalone utilities such as `HexColor`, `ScreenLayout`, `TaskQueueMixin`, `CoreLockService`, and `LoadingOverlay` use dedicated sub-imports so you always see what a file depends on.
  </Accordion>
