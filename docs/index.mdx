## What is Butterfly?

Butterfly is a collection of optional packages, not an application framework. Use the CLI to scaffold Dart files, or use individual Flutter libraries without running the CLI.

These guides describe the repository implementation, including its current limitations. A published CLI release or a previously pinned Git dependency can behave differently from your checkout.

## Choose a starting point

| `auth_management_firebase_google` | Native Google sign-in mixin for Firebase |
| `auth_management_oauth2` | OAuth2 sessions and grant mixins |
| `auth_management_provider_riverpod` | Explicit bridge to Riverpod user state |

## Structure and adoption

The CLI's project folders belong under `lib/`: `models`, `services`, `screens`, and `widgets`. They are a scaffolding convention, not a requirement imposed on library consumers.

You own concrete services such as `AuthService` and `CoreService`. Butterfly supplies base classes, not a built-in static `AuthService.signIn()` facade. Imports are explicit: the core barrel exports service base classes, but utilities such as `HexColor` and `TaskQueueMixin` need their own imports.

Adopt only the packages you need. Removing a package means replacing the APIs your application uses; it is not automatically dependency-free or a guaranteed copy-and-paste migration.

## Documentation maintenance

This site uses root `docs.json`, MDX files under `docs/`, YAML `title` and `description` frontmatter, and root-relative page links, following the [current docs.page authoring guide](https://use.docs.page/authoring/write).

From the repository root, validate MDX, metadata, links, and assets with:

```bash
npx --yes @docs.page/cli@latest check
```

That validates the site, not Dart behavior. Run the analyzer and relevant package tests as well; see [verification](/features#verification). Local edits do not publish until they are committed and pushed to the branch docs.page serves.
